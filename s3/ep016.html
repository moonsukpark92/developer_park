GSD —
AI가 잊어먹는 걸
막아주는 플러그인

AI한테 일을 시키다 보면 — 자꾸 잊어먹는다. 어제 하던 일이 오늘 사라진다.
여러 일을 동시에 시키면 컨텍스트가 무너져서 처음부터 설명을 다시 해야 한다.
이 문제를 한 방에 해결한 운영 체계가 있다. 이름은 GSD.
바이브 코딩하는 비개발자한테 — 이게 없으면 이 시리즈도 못 썼다.

Chapter 01

AI한테 일 시키다 보면
— 자꾸 잊어먹는다

AI랑 코딩을 하다 보면 — 처음엔 마법 같다. "이거 만들어줘" 하면 만들어준다. "여기 고쳐줘" 하면 고쳐준다. 근데 일이 커지기 시작하면 — 뭔가 무너진다.

어제 하던 일을 오늘 다시 시키면 "네? 그게 뭔가요?" 한다. 어제까지 알던 파일 구조를 모르고, 어제 결정한 디자인 톤을 까먹고, 어제 만든 함수를 모르고 또 만든다. 대화창은 5천 줄이 넘어가면 앞부분이 흐려진다.

더 큰 문제는 — 일을 여러 개 동시에 굴리는 경우다.
박대표 시리즈를 쓰면서 동시에 회사 ERP 자동화도 하고, 유튜브 채널 런칭 계획도 짜고, 손해배상 소송 자료도 정리한다. AI한테 이걸 다 시키면 — 지금 어디 일을 하고 있는지 자기도 모른다.

실제로 자주 듣는 말

"이전 대화의 맥락을 모르겠습니다. 무엇을 하시려는지 다시 한번 설명해주세요."
— 또야?

이게 바이브 코딩하는 비개발자가 마주치는 진짜 벽이다. 코딩이 어려운 게 아니다. AI랑 같은 페이지에 있게 만드는 게 어렵다.

Chapter 02

GSD라는 운영 체계를 만났다
— Get Sh*t Done

Claude Code 환경에서 쓰는 GSD라는 운영 체계가 있다. "Get Sh*t Done." 이름이 직설적이다. 일을 끝내라. 이 운영 체계가 하는 일은 단순하다 —
AI가 잊어먹지 않도록, 모든 결정·진행·다음 할 일을 파일에 영구 기록한다.

적용하면 프로젝트 안에 .planning/ 폴더가 생긴다. 그 안에 — 지금 무슨 단계인지, 어디까지 했는지, 다음에 뭘 해야 하는지, 무엇을 절대 하면 안 되는지 가 자동으로 적힌다. 사람이 적는 게 아니라, AI가 적는다. 그것도 매 작업마다.

.planning/ 구조
.planning/
├─ HANDOFF.json # 다음 세션이 self-sufficient하게 재개
├─ PROJECT_IDENTITY.md # 프로젝트의 불변 정체성 (LOCKED)
├─ intel/ # 코드베이스 분석 — tech, arch, quality, concerns
├─ phases/ # 단계별 계획 + 실행 + 검증 기록
└─ roadmap/ROADMAP.md # P0~P3 우선순위 로드맵

처음엔 "이게 뭐 별거야?" 싶었다. 폴더 하나 만든 거잖아.
근데 — 이 폴더 하나가 모든 걸 바꿨다.

Chapter 03

잠깐 — 이 글 자체가
유튜브 → 제미나이 → Claude의 결과다

여기서 한 번 멈춘다. 사실 이 GSD라는 도구를 알게 된 과정 자체가 — 이전 에피소드(EP014)에서 말했던 그 패턴 그대로다.

유튜브에서 "바이브 코딩 필수 플러그인 3가지" 같은 영상을 봤다. 세 가지 다 좋아 보였다. 근데 — 다 깔 수는 없다. 어느 게 진짜 우리한테 맞는지 모른다.

선택의 자동화
# 1단계 — 영상 링크만 던졌다
박대표 ▸ Gemini, 이 영상에 나온 3가지 플러그인 분석해라
[gemini] 영상 분석 + 3개 플러그인 검색 보강 + 비교표
# 2단계 — 결과를 MD로 받아 Claude한테 넘겼다
박대표 ▸ Claude, 우리 회사 상황에 가장 맞는 거 골라라
[claude] 우리 컨텍스트(비개발자, 다중 프로젝트) 분석 + 추천
✓ 선택 결과: GSD (Get Sh*t Done) — 컨텍스트 관리 최적

나는 3개 플러그인 자체에 대한 글도 안 읽었다. 유튜브 영상도 한 번만 봤다. 그런데 — 우리 회사에 가장 맞는 플러그인이 무엇인지에 대한 답은 손에 들어왔다.

"바이브 코딩에 필요한 도구를 선택하는 일 자체가 — 이미 바이브 코딩으로 처리되고 있다."
이게 EP014에서 말한 "AI에게 AI를 학습시키는" 방법의 진짜 모습이다. 도구가 도구를 추천하고, AI가 AI 사용법을 정리한다.

"유튜브 영상 1편 +
Gemini 분석 + Claude 선택 →
도구 선정 끝. 30분."

Chapter 04

GSD의 진짜 정체 —
설치 프로그램이 아니다

Claude가 정리해 준 결과를 보고 알았다.
GSD는 기술적으로 '설치형 프로그램'이 아니다. Claude의 컨텍스트(기억력) 한계를 극복하기 위한 운영 체계에 가깝다. 쉽게 말하면 — "AI를 어떻게 쓸지에 대한 약속" 자체다.

이 프레임워크의 핵심 단어는 "Context Rot(컨텍스트 썩음)"이다. 대화가 길어지면 — AI의 답이 점점 흐려지고, 어제 한 말과 오늘 한 말이 안 맞기 시작한다. 이게 썩는다는 표현이다. GSD는 이걸 막기 위해 작업을 분리된 세션에서 수행하게 만든다.

구조는 단순하다 — 지휘관(Commander)과 실행자(Agent)를 분리한다.

ROLE 01

Commander · 지휘관

메인 세션. 큰 그림·계획·검토만 한다. 디버깅 삽질이 들어오지 않는다. 수명이 길다.

ROLE 02

Agent · 실행자

서브 세션. 새 채팅창에서 한 작업만 격리 실행. 끝나면 결과만 메인으로 들고 간다.

그래서 실전 운영은 3단계 워크플로우로 굴러간다.

① Plan (메인)메인 세션에서 요구사항을 말한다 → 지휘관이 "전용 프롬프트"를 만들어 준다
② Execute (서브)완전히 새로운 채팅창을 연다 → 전용 프롬프트를 첫 메시지로 넣고 작업한다 (컨텍스트 격리의 핵심)
③ Review (메인)서브에서 완성된 결과만 메인으로 가져와 동기화한다

처음엔 "매번 새 창 여는 거 귀찮은데?" 싶었다. 맞다. 귀찮다. 근데 — 프로젝트가 커질수록 AI가 이전 대화 때문에 헷갈리는 현상이 완벽하게 막힌다.

메인엔 결과만 남고, 과정(디버깅 삽질)은 서브에서 소모된다. 그래서 메인 세션의 수명이 비약적으로 늘어난다. 이게 GSD가 진짜로 사주는 가치다. 토큰 절약이 아니라 — 판단력의 보존이다.

"Context Rot을 막는 가장 단순한 방법 —
썩기 전에 옮겨심는다.
이게 GSD의 본질이다."

Chapter 05

핵심은 HANDOFF.json
— "다음 세션 너에게"

GSD의 진짜 무기는 HANDOFF.json이다.
세션이 끝나기 전에 — 지금까지 한 일, 남은 일, 막힌 일, 사람이 결정해야 할 일, 다음 세션이 반드시 먼저 읽어야 할 문서 순서까지 자동으로 기록된다.

그리고 다음 세션이 시작되면 — 새 Claude는 그 파일을 먼저 읽는다. "아, 어제까지 여기까지 했고, 지금 막힌 건 이거고, 다음은 이거 하면 되겠네."
처음부터 설명할 필요가 없다.

HANDOFF.json · 실제 발췌
# 유튜브 채널 런칭 계획 세션 종료 시점
"completed_tasks": [
{"id": 1, "name": "헌법 + 5개 전략 + 자동화 청사진 13개 문서 작성", "status": "done"},
{"id": 5, "name": "ffmpeg 노이즈 제거 검증 (36분 → 26초, 87배 실시간)", "status": "done"},
...
],
"remaining_tasks": [
{"id": 8, "name": "D1: YouTube 채널 개설", "status": "not_started"},
{"id": 11, "name": "D3: ElevenLabs PVC 학습 신청", "status": "not_started"},
...
],
"blockers": [{"description": "FFmpeg PATH 갱신 필요", "workaround": "..."}],
"human_actions_pending": [{"action": "ElevenLabs 결제 ($22/월)", "blocking": true}]

이게 정말 무서운 부분이다. AI는 어차피 잊어먹는다. 이 사실을 인정하고 — 잊어먹어도 괜찮은 구조를 만든 거다.

박대표 시리즈도, 유튜브 런칭 계획도, 회사 자동화도 — 각각 .planning/ 폴더가 따로 있다. 어떤 일을 하다가 다른 일로 넘어갔다가 일주일 뒤에 돌아와도, 정확히 어디서 멈췄는지 그 폴더가 알고 있다.

"AI의 기억력을 신뢰하지 마라.
대신 — AI가 기억하도록 강제하는 시스템을 만들어라."

Episode 016 — 핵심 1

AI는 잊는다 —
그래서 파일에 박는다

GSD는 천재 AI가 아니다. 단순한 규칙이다.
"끝나기 전에 무조건 적어라. 다음 세션은 무조건 읽어라."
이 단순한 규칙 하나가 — 컨텍스트 문제를 거의 다 해결했다.

Chapter 06

슬래시 커맨드 — 일하는 방식이
완전히 바뀌었다

GSD를 적용하면 슬래시(/) 하나 치고 명령어를 부른다. 이게 평소에 입력하던 자유 문장보다 — 훨씬 정확하고, 훨씬 빠르고, 훨씬 안정적이다. 자주 쓰는 명령어 몇 개는 거의 매일 친다.

/gsd:new-project새 프로젝트 시작 — 정체성·환경·로드맵을 한 번에 잡는다
/gsd:plan-phase한 단계의 계획을 세운다 — 작업 분해 + 의존성 + 목표 역산 검증
/gsd:execute-phase계획을 실제로 실행 — 원자적 커밋 + 체크포인트 + 일탈 감지
/gsd:resume-work전 세션에서 멈춘 일을 정확히 그 자리에서 다시 시작
/gsd:pause-work중간에 끊을 때 — 다음 세션을 위한 인계서를 자동 생성
/gsd:next"지금 뭐 해야 해?" — 알아서 다음 단계로 라우팅
/gsd:progress전체 진행률 + 막힌 곳 + 다음 액션을 한 화면에
/gsd:autonomous남은 단계를 전부 자동 실행 — 잠자는 동안 일이 끝나 있다
/gsd:audit-uat계획 대비 실제 산출물 검증 — 빠뜨린 게 있는지 검사
/gsd:code-review변경된 코드 자동 리뷰 — 버그·보안·코드 품질 점검

예전엔 "이거 해줘 / 이거 어떻게 됐어 / 이거 다음에 뭐였지?" 를 매번 자유 문장으로 물었다. 말이 길어지면 의도가 흐려지고, 다른 일과 섞인다.
슬래시 명령은 — 의도를 한 단어로 못 박는다. /gsd:next 한 줄이 "이전 세션 인계서 읽고, 미완 작업 찾아서, 다음 단계 추천해주세요" 와 같다.

Chapter 07

실제로 — 이 시리즈도
GSD로 굴러간다

이 블로그 시리즈가 어떻게 굴러가는지 보여준다.
박대표 시리즈 폴더 안에는 — .planning/, marketing/, devlogs/ 세 개의 GSD 영역이 있다.

Area 01

.planning/ — 사이트 운영

P0~P3 로드맵: 민감정보 grep 자동화, 푸시 전 lint, 백업 미러, 검색 기능 도입까지 6개월 계획

Area 02

marketing/ — 유튜브 런칭

헌법(00_philosophy.md) + 전략 5종 + 자동화 청사진 + 음성/녹화/편집기 가이드 = 13개 문서

Area 03

devlogs/ — 매 세션 기록

각 세션 종료 시 의무 작성 — 무엇을, 왜, 어떻게 했고 다음에 뭐 할지

에피소드 한 편을 쓰면 — 그 작업의 모든 결정이 devlogs/YYYY-MM-DD.md 에 적힌다. 네비 패치, 마스킹 룰, 톤 결정, 미해결 사항까지.
다음에 새 에피소드를 쓸 때 — Claude는 이 devlog들을 먼저 읽는다. 그래서 톤이 흔들리지 않는다. 마스킹이 빠지지 않는다. 같은 실수를 반복하지 않는다.

"AI한테 이 시리즈를 쓰게 하면 톤이 안 맞을 텐데?" 그렇게 되지 않는 이유다.
AI가 매번 똑똑해서가 아니다. 매번 같은 문서를 먼저 읽어서다.

Before · GSD 없을 때

매 세션 처음부터

새 대화창을 열 때마다 톤·규칙·진행 상황 다시 설명. 대화 중간에 잊어버리면 또 설명. 여러 프로젝트가 섞이면 어디 일인지도 모름.

After · GSD 도입 후

파일이 다 알고 있다

/gsd:resume-work — 어디서 멈췄는지, 다음 뭐 할지 자동 복원. 프로젝트별 .planning/ 폴더가 자기 일을 자기가 기억. 실수 재발 거의 0.

Chapter 08

가장 좋아진 게 무엇이냐
— 컨텍스트가 흩어지지 않는다

GSD를 쓰고 가장 좋아진 게 뭐냐 — 한 마디로 흔들리지 않는다.

나는 코딩하다가 마케팅 일로 넘어갔다가 손해배상 자료 정리로 갔다가 다시 블로그를 쓴다. 하루에도 4~5개 컨텍스트가 바뀐다. 예전엔 — 옮길 때마다 컨텍스트가 흘렀다. 어제 마케팅 회의에서 결정한 게 오늘 블로그 톤에 묻어 들어오고, 소송 자료 정리 톤이 코딩 결정에 묻어 들어왔다.

지금은 — 각 프로젝트가 자기 컨텍스트를 자기 폴더에 가두고 있다. 마케팅 작업하다 블로그로 넘어가면 /gsd:resume-work 하나 치면 된다. Claude는 블로그 폴더의 .planning과 devlogs를 다시 읽고 — 그 톤으로 일한다. 섞이지 않는다.

진짜 가치

GSD는 신기술이 아니다. "적어두면 잊지 않는다"는 너무 당연한 사실을 —
AI한테 강제 적용한 시스템일 뿐이다.
근데 이 당연한 게 — 바이브 코딩의 한계를 깨는 가장 큰 무기였다.

Chapter 09

시작하는 법 — 그리고
먼저 알아야 할 3가지

이 글을 보는 다른 비개발자 사장님께 한 마디.
Claude Code를 쓰고 있다면 — 지금 당장 GSD를 도입해 봐라. 소스 프롬프트는 mshumer의 GSD GitHub 저장소(github.com/mshumer/gsd)에 공개되어 있다. Claude Project를 새로 만들고 [Set custom instructions]에 Commander 프롬프트를 붙여 넣으면 끝이다.

Claude Code 환경이라면 — 슬래시 커맨드 형태로도 같은 운영 체계를 쓸 수 있다. 어느 쪽이든, 본질은 같다 — 메인 세션은 지휘관, 서브 세션은 실행자.

START 01

/gsd:new-project

새로 시작하는 프로젝트라면 이 한 줄로 .planning 구조 자동 생성

START 02

/gsd:ingest-docs

기존에 흩어진 PRD·SPEC·메모를 GSD가 일괄 흡수해서 정리

START 03

/gsd:plan-phase

큰 일을 한 번에 시키지 말고 단계로 쪼개라 — 그게 GSD의 사용법

START 04

/gsd:next

막혔을 때 — "지금 뭐 해야 해?" 한 마디면 다음 단계로 라우팅

그리고 — 시작하기 전에 솔직하게 알려야 할 3가지 주의사항이 있다. 나도 처음에 모르고 시작해서 한참 헤맸다.

CAUTION 01

귀찮음을 견뎌야 한다

매번 새 채팅창 여는 게 번거롭다. 처음엔 "그냥 한 창에서 다 하면 안 되나?" 생각이 든다. 안 된다. 프로젝트가 커질수록 그 귀찮음이 회사를 살린다.

CAUTION 02

파일 동기화를 잊지 마라

서브 세션에서 코드를 수정했다면, 메인 프로젝트의 파일(Project Knowledge / 로컬 파일)도 최신으로 반영해야 한다. 안 하면 지휘관이 옛날 정보로 판단한다.

CAUTION 03

토큰은 결국 절약된다

메인엔 결과만, 서브엔 과정만 — 이 분리만 잘 지키면 메인 세션의 수명이 비약적으로 늘어난다. 토큰 효율이 따라온다.

"혼자 알면 사라진다. 같이 알면 변한다.
GSD도 그래서 공유한다 — 이건 도구 자랑이 아니라
살아남는 방법의 공유다."

바이브 코딩이 진짜 가능해진 건 — Claude가 똑똑해져서가 아니다.
Claude의 한계(잊어먹음)를 인정하고, 그걸 보완하는 외부 시스템(GSD)이 등장했기 때문이다. 도구가 도구를 보완하는 시대 — 그게 지금이다.

한 사람의 머릿속에 모든 걸 넣지 마라. 한 AI의 컨텍스트에 모든 걸 넣지도 마라. 파일에 박아라. 폴더에 분리해라. 시스템에 맡겨라.
이게 — 비개발자가 AI랑 일하는 가장 안정적인 방법이다.
