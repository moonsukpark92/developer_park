Chapter 01

1인 대형 프로젝트
— 이런 문제들이 터진다

바이브 코딩으로 2~3주 달리면 뭔가 되는 것 같다.
근데 외부 환경에서 여러 사람이 쓰는 소프트웨어를 만들기 시작하면 얘기가 달라진다. 주 모듈이 너무 커지고, DB 구조가 처음 설계와 달라지고, 세션을 여러 개 열다 보면 서로 같은 코드를 건드려 엉킨다. 나도 겪었다. 다들 겪는다.

🔄

멀티 세션 충돌

기다리기 지루해서 세션 여러 개 열었다가 서로 같은 코드를 건드려 엉킨다. 나중에 원인도 모르는 대형사고가 된다.

🗄️

DB 구조 설계 실수

처음부터 완벽하게 설계 안 하면 나중에 로딩 시간이 폭발한다. 연결 구조가 꼬이면 자료가 다 엉키고, 다시 밀어야 한다.

⚠️

깃허브 실수 → 코드 증발

로컬과 서버 동기화 안 된 걸 까먹고 잘못 푸시하면 그쪽 베이스로 개발한 게 다 날아간다. 기본 명령어는 반드시 숙지해야 한다.

🧩

예외 규정 누적 → 폭발

간단한 재고장에도 예외 규정 하나씩 추가하다 보면 걷잡을 수 없이 복잡해진다. AI도 원인 찾는 데 한참 걸리고 에너지가 소비된다.

"꼬이게 되면 원인도 모르고
AI도 한참 걸린다 — 에너지가 엄청나게 소비된다."

Chapter 02

계획서는 살아있어야 한다
— 만들고 끝이 아니다

처음 계획서가 재고장 수준이었다. 지금은 업무통합 소프트웨어로 확장됐다. 그 확장되는 스토리 전체가 계획서에 담겨있다.

뭔가 생각날 때마다, 작업이 끝날 때마다 — 기존 계획서를 업데이트한다. 그래야 나중에 문제가 생겨도 계획서를 따라 되돌아올 수 있다. 계획서 없이 빠르게만 가면 어느 순간 길을 잃는다.

여러 세션을 열어서 작업하다 보면 — 세션끼리 같은 부분을 건드리게 된다. 서로 다른 방향으로 고치다 보면 코드가 엉긴다. 이게 사소해 보이지만 프로그램적으로는 대형사고다.

①

DB 구조 — 중간에 변화가 올 때마다 반드시 한 번씩 점검

처음에 완벽하지 않아도 된다. 단, 변화가 생길 때마다 구조를 들여다보지 않으면 나중에 되돌릴 수 없는 문제가 생긴다.

②

작업 완료 후 → Claude Code가 개발 일지 자동 작성

세션이 죽어도, 깃허브가 꼬여도 — 일지가 남아있으면 추적된다. AI가 스스로 오늘 뭘 했는지 기록하게 만든다.

③

개발 일지 → 계획서 업데이트 → 중간 전체 리뷰

계획서가 계속 살아서 보강된다. 중간에 한 번씩 전체를 리뷰 돌리면 방향이 흐트러지지 않는다.

# 멀티 세션 사고 — 실제 재현
Session A: 결제 모듈 수정 중...
Session B: (동시에) 결제 모듈 DB 스키마 변경...
✗ Conflict — 두 세션이 같은 파일을 덮어씀
✗ 어느 버전인지 알 수 없음 — 원점 복구 시작
# 원칙: 세션 하나씩. 완료 후 커밋. 그다음 시작.
✓ 세션 분리 + 섹션별 커밋 → 충돌 없음

2부 핵심

코드를 공부하지 말고
업무를 더 깊이 이해하라

코드는 AI가 짠다.
계획서, DB 설계, 문제를 보는 시각 — 이건 내가 해야 한다.
그게 바이브 코딩의 진짜 실력이다.

Chapter 03

AI가 "된다"고 해도
— 반드시 직접 검토해야 한다

YouTube 최신 기술을 다 공부해서 내 것으로 만든다는 건 불가능하다.
그래서 Gemini가 분석하고, Perplexity로 보강해서 .md로 만들어 Claude Code에게 준다. "우리 상황에 적용 계획서를 만들어라."

여기서 반드시 해야 하는 것이 있다.
그 계획서를 꼼꼼하게 직접 읽어봐야 한다.

"안 된다고 하는 AI는 잘 없다.
위험 부담이 있어도 된다고 한다."

그걸 그냥 믿고 진행하면 — 나중에 되돌리는 데 시간이 엄청나게 든다. 그 기능이 꼭 필요한지, 우리한테 맞는지를 직접 판단해야 한다. AI가 해주는 게 아니다.

지난 한 달 동안 이 부분에서 상당히 많은 실수를 했고, 많이 배웠다.

Chapter 04

바이브 코딩의 진짜 강점
— 코딩하면서 시각이 달라졌다

프로그램을 만들면서 느낀 게 있다.
"우리 회사에 나만큼 일을 속속들이 아는 사람이 있는가?"

그리고 반대로 — "아, 이 부분은 내가 오래했지만 생각이 짧았구나."

코딩을 하면서 문제를 보는 시각이 달라졌다.
나는 잘 알지만, 이걸 모르는 사람이 쓰면 어디서 실수할까?
이 질문이 실제 기능에 반영되기 시작했다. 그러면서 바이브 코딩이 다시 한번 강력해진다.

핵심 인사이트

바이브 코딩은 코딩 기술이 아니다.
이건 업무 전문성 × AI의 조합이다.
자신의 업무를 가장 잘 아는 사람이 결합됐을 때
가장 강력한 시너지가 생긴다.

요즘엔 이걸 "바이브 엔지니어링"이라고도 부른다. 코드를 짜는 게 아니라 — 시스템을 설계하고 AI를 지휘하는 것. 그게 지금 내가 하고 있는 일이다.

2~3달이면 누구나 이 고비를 겪는다.
이 고비를 넘어가야 제대로 된 바이브 엔지니어링이 시작된다.
